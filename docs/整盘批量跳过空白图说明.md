# 整盘批量：跳过盘外空白图

> 实现：`python_core/tile_scheduler.py`（调度，有单测）+ Bridge `PythonSahiPipeline` 循环接入 + 检测页复选框「整盘批量：跳过盘外空白图」
> 状态：Python 部分已测；**C# 改动未在 .NET 环境编译**，请在本机构建后用一盘整盘批量跑一次。

## 1. 一盘真实数据说明了什么

用一盘完整批量的 `summary.csv`（576 张，51355 颗）分析：

| 项 | 数值 |
|----|------|
| 含钻 tile / 0 颗 tile | 422 / 154 |
| 整批总耗时 | 61.7 min（检测 36.6 + 分类 25.1） |
| 0 颗 tile 占用的时间 | 9.5 min（**15.4%**） |
| 检测耗时（0 颗 vs 含钻） | 中位 3.39 s vs 3.66 s —— 与钻石数几乎无关，空图一样要花 ~3.4 s |
| 分类每颗耗时 | ≈ 25 ms（满盘 tile 约 3.3 s / 135 颗），此前观察到的 190–270 ms/颗已不存在 |
| 占用图形状（行优先编号） | 光滑的圆，占 23×23 格，靠网格左上；**蛇形编号会出现交替锯齿，已排除** |

**天花板**：即使把 154 张空图一张不剩全部省掉，也只能省 15.4%。所以这一步的价值是"稳妥地拿到 7%~15%"，不是大幅提速；更大头在检测本身（见 §5）。

## 2. 做法：邻域扩展 + 抽检回查

1. 从网格中心附近开始处理；
2. 只有**检出钻石**的 tile，才把它还没处理的 8 个邻居排进队列；
3. 队列空了就结束。没被排进来的 tile 离任何含钻 tile 都隔着一整张图，而圆盘是凸的，不会在中间断开，所以它们是盘外空白；
4. **抽检回查**：结束后随机挑 3 张被跳过的（优先离盘最近的）真正检测一次。抽到钻石就判定前提不成立（盘不凸 / 编号规则不符 / 批次混了别的盘），立刻退回处理全部剩余图像。

**不依赖任何图像阈值，不需要标定**。对一盘真实占用图回放：

| 设置 | 处理张数 | 跳过 | 节省 | 漏检 |
|------|---------|------|------|------|
| 不抽检 | 502 | 74 | 4.6 min（7.5%） | 0 / 422 |
| 抽检 3 张（默认） | 505 | 71 | 4.5 min（7.3%） | 0 / 422 |

跳过的 74 张是"自己和 8 个邻居都是空"的深盘外图；紧贴盘边的 80 张空图必须检测一次才知道它是空的（这是不用图像信息所付出的代价）。

## 3. 安全性

| 情形 | 行为 |
|------|------|
| 随机 300 个位置/大小的盘（含偏心、被网格截断） | 漏检 0 |
| 网格中心 tile 恰好是空的（盘在角落） | 按离中心由近到远逐张找到第一张含钻图再扩展；最坏退化为逐张处理，不会更慢 |
| 某张检测报错 | 按"可能有钻"处理，继续向邻居扩展 |
| 盘外有孤立的一块有钻 tile（不连通） | 邻域扩展会漏；抽检抽到就退回全处理（测试里用 400 张抽检强制验证了这条路径；默认 3 张抽到的概率取决于孤岛位置，**所以这类异常靠抽检只是概率性兜底**） |
| 文件名取不出 tile 编号 / 编号重复或越界 | 自动关闭，逐张处理 |
| 本批只有一部分图（覆盖 < 80% 网格） | 自动关闭，逐张处理 |
| 混入取不出编号的杂图 | 杂图一律处理 |

**前提**：文件名末尾是 tile 编号（`1.jpg … 576.jpg`），编号按行优先。若实际是蛇形，邻接关系会错位——此时抽检会很可能发现问题，但请务必先用 `disk_stitch` 的编号规则识别确认一次。

## 4. 对输出的影响

- `summary.csv` 仍然 576 行、表头不变；被跳过的图是 0 颗、各项耗时 0（可与"真检测过的空图"区分：后者耗时约 3.4 s）；顺序仍为原输入顺序。
- 被跳过的图**不创建输出子目录**（真检测过的空图仍是 `{stem}_无目标`）。下游 `disk_stitch`、均匀度分析按"有 detect_boxes.json 的目录"读取，不受影响。
- 状态栏/日志会显示"跳过 N 张盘外空白图，抽检 3 张"；抽检失败会提示检查编号规则。
- 设置：检测页「处理模式」里的复选框（默认开，记住选择）；网格行列数和抽检张数在 `app_config.json` 的 `tile_grid_rows / tile_grid_cols / skip_audit_count`。
